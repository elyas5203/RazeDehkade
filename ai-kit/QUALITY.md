# کیفیت و تعریف پایان

## ماتریس بررسی متناسب
| تغییر | بررسی مناسب |
|---|---|
| متن یا سبک کوچک | بازخوانی و مشاهده خروجی |
| منطق | تست هدفمندِ ورودی/خروجی و حالت مرزی |
| API | قرارداد، خطا، مجوز، مصرف‌کننده و یکپارچگی مرتبط |
| UI | build موجود، مرورگر، تعامل، موبایل/دسکتاپ، کیبورد و RTL |
| احراز هویت/پول | آزمون منفی، تکرار، همزمانی مرتبط و حفظ سازگاری |
| مهاجرت | dry-run روی نمونه نماینده، داده پیشین، rollback |
| عملکرد | baseline و مقایسه هم‌محیط با حجم داده معلوم |

فرمان را از package/config واقعی استخراج کن؛ `npm test` را برای هر پروژه حدس نزن. پیش از آزمون یکپارچگی مقصد اتصال را بشناس. محیط واقعیِ هم‌نوع برای موارد وابسته به رفتار engine لازم است؛ آزمون واحد را بی‌جهت سنگین نکن.

## ثبت نتیجه
برای هر بررسی: فرمان یا روش دقیق، محیط، زمان، نتیجه pass/fail/blocked/not-run و خلاصه خطا. خروجی خام حجیم را در حافظه نریز. «اجرا نشد چون سرویس موجود نبود» از «تأیید شد» متفاوت است. نتیجه تست پیش از تغییر را به نسخه بعد تعمیم نده.

## چک پایان
- معیار پذیرش پوشش دارد و خارج از محدوده روشن است.
- diff شامل تغییر نامرتبط یا راز نیست؛ کار قبلی حفظ شده است.
- شکست‌های جدید رفع شده‌اند یا کار ناتمام صریح گزارش شده است.
- مستندات قرارداد/تصمیم و STATE در صورت نیاز تازه‌اند.
- deploy و production فقط اگر واقعاً انجام و مشاهده شده گزارش می‌شوند.
