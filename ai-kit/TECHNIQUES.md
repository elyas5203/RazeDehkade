# روش‌های عملی پرامپت‌نویسی
این‌ها انتخاب طراحی این بسته‌اند؛ نام بعضی الگوها توضیحی است و ادعای استاندارد رسمی ندارد.

## ۱. نتیجه و سنجش پیش از جزئیات
به جای «ورود را درست کن»: «کاربر ثبت‌شده با رمز درست وارد شود؛ رمز غلط پیام عمومی بدهد؛ نشست قبلی معتبر بماند؛ تست مسیر موفق و رد دسترسی اجرا شود.» راه‌حل داخلی را فقط اگر الزام واقعی است تحمیل کن.

## ۲. زمینه در سه لایه
همیشگی: CORE کوتاه. پروژه: PROJECT و STATE. وظیفه: فقط TASK، کد و قرارداد مرتبط. تاریخچه قدیمی به archive منتقل شود و پیوند بماند. شماره خط‌ها نقشه دائمی مناسبی نیستند؛ مسیر و نماد را نگه دار.

## ۳. قرارداد داده پیش از مصرف‌کننده
نمونه: `GET /items -> {items: Item[], nextCursor: string|null}`. پیش از پیاده‌سازی، هویت Item، مجوز، خطا و صفحه‌بندی را با قرارداد واقعی پروژه تطبیق بده. برای backend موجود قرارداد جدید اختراع نکن. داده mock برای طراحی است، نه اثبات اتصال.

## ۴. شاهد پیش از patch
دستیار فایل و تابع هدف و علت تغییر را مشخص کند. نقل تمام کد به چت لازم نیست. patch محدود و بازبینی diff از بازتولید طولانی فایل مفیدتر است. هیچ درصد بهبود عمومی برای این روش تضمین نمی‌شود.

## ۵. حلقه بازخورد
هدف -> تغییر کوچک -> بررسی -> مشاهده خطا -> اصلاح. برای UI، رندر و تعامل؛ برای API، وضعیت و schema؛ برای باگ، بازتولید؛ برای عملکرد، baseline و اندازه‌گیری هم‌محیط. به جای «خودت مطمئن شو» روش مشاهده را بنویس.

## ۶. بازبینی مخالف
برای تغییر مهم بپرس: «با کدام ورودی این راه‌حل می‌شکند؟ چه چیزی سازگاری قبلی را نقض می‌کند؟» بررسی مستقل وقتی واقعی است که ابزار و فرد/ایجنت جدا وجود داشته باشد. بازخوانی خودِ دستیار استقلال ایجاد نمی‌کند.

## ۷. توقف و سؤال هدفمند
سؤال فقط وقتی پاسخ بر رفتار مهم اثر دارد: «پس از لغو پرداخت، اعتبار باید برگردد یا منتظر تسویه بماند؟» برای نام فایل موقت و جزئیات قابل بازگشت کار را متوقف نکن. اگر کاربر فقط طرح خواسته وارد اجرا نشو.

## ۸. ابزار و مدل
هیچ نام مدل، دستور slash یا پارامتر API را بدون مستندات نسخه جاری ضروری نکن. اگر ابزار اینترنت ندارد، تحقیق تازه را ادعا نکند. Markdown محدودیت context، مجوز و قابلیت میزبان را حذف نمی‌کند.
