# بازبینی و همکاری اختیاری
پیش‌فرض یک دستیار است. استفاده از ایجنت واقعی فقط با اجازه کاربر یا قواعد معتبر محیط و در صورت وجود ابزار. این سند خودش درخواست delegation نیست.

## دیدگاه‌های انتخابی
| دیدگاه | زمان استفاده | پرسش محوری |
|---|---|---|
| محصول | ابهام رفتار | آیا مسئله درست حل شد؟ |
| معماری | مرز ماژول/قرارداد | آیا مصرف‌کننده‌ای می‌شکند؟ |
| امنیت | ورودی، نقش، راز | آیا مسیر رد دسترسی آزموده شد؟ |
| داده | schema، پول، همزمانی | آیا تکرار و rollback داده را خراب می‌کند؟ |
| تست | تغییر رفتار | آیا آزمون شکست واقعی را می‌گیرد؟ |
| تجربه کاربر | UI | آیا خطا و بازیابی روشن است؟ |
| دسترس‌پذیری | UI | آیا بدون ماوس قابل استفاده است؟ |
| عملکرد | گلوگاه مشاهده‌شده | baseline و اندازه‌گیری چیست؟ |
| عملیات | deploy/config | چگونه تشخیص و بازگشت می‌دهیم؟ |

فقط دیدگاه مرتبط را انتخاب کن. کار ساده نیاز به تعیین تکلیف ۵۰ نقش ندارد. اگر کاربر بررسی کامل ۵۰نقشی خواست، سند قبلی او را جدا معرفی و هزینه/دامنه را روشن کن؛ این بسته آن سند را خودکار فعال نمی‌کند.

## اگر همکاری واقعی مجاز و ممکن بود
مالک هماهنگی یک نفر باشد. هر مأموریت: هدف، فایل‌های مجاز، منع تغییر فایل مشترک، معیار خروجی و محدودیت. کارهای مستقل را موازی و کارهای وابسته را ترتیبی انجام بده. مالک نوشتن هر فایل روشن باشد؛ جداسازی context به معنی جداسازی filesystem نیست. برای تغییرات برخوردکننده از checkout جدا یا ادغام ترتیبی استفاده کن. هیچ reset کور انجام نشود.

پاسخ هر بررسی: وضعیت، محدوده، روش، یافته، شاهد، اثر، اطمینان، اصلاح پیشنهادی و چیزی که بررسی نشد. تعارض با شاهد و بازتولید حل شود، نه رأی اکثریت. پس از دو دور بی‌نتیجه، اختلاف و بررسی لازم را ثبت کن. ادغام‌کننده تست یکپارچه را اجرا کند؛ موفقیت جزء موفقیت کل نیست.

## بدون ابزار چندایجنتی
همان دستیار دیدگاه‌ها را به ترتیب بررسی کند و خروجی را «بازبینی تک‌دستیار» بنامد. استقلال، تعداد agent و آزمون انجام‌نشده جعل نشود.
